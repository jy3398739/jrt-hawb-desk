# 主分单审核台 · 整体流程与公司 IT 对接说明

> 面向：公司 IT / 接口提供方。用途：说明"HAWB 分单识别 → 主分单核对 → 回传"的完整流程、当前实现状态，
> 以及**需要 IT 侧提供哪些接口、报文长什么样、还有哪些口径要对齐**。
> 版本：2026-09-23。代码：`release/hawb_extractor`。

---

## 一、这套系统在做什么

围绕航空货运单（MAWB 主单 / HAWB 分单）做两件事：

1. **识别提取**：把分单票面（PDF / 扫描件 / Excel 电子单）用视觉大模型读成结构化字段 JSON（40 字段，航空口径）。
2. **核对与回传**：人工在审核台上核对提取结果，确认无误后把 JSON 回传公司系统；后续由录入员做主单↔分单的一致性核对。

涉及**三类账号角色**（登录是唯一门禁，口令 pbkdf2 哈希存本机 `users.json`，不入库不外传）：

| 角色 | 谁 | 能做什么 |
|---|---|---|
| 管理员 admin | 运维 | 切换模型、管理子账号（下发/重置口令、增删）|
| 制单员 reviewer | 8 位制单员 | 上传分单 → 看票面 → 核对航空口径字段 → **点提交回传公司** |
| 录入员 inputter | 刘明 / 郭健康 / 郭旭 | **不上传**；按主单号从公司取回主单+分单 JSON → 打开本机分单原件对票面核对 → 有修改权 |

## 二、端到端流程（含当前实现状态）

### 阶段 1：制单员上传提取并回传（现有管道 + 本期已落）

```
制单员登录(/) → 上传分单文件
  → 服务端提取(L0归档原件→L1转录→L2原文40字段→L3航空口径→质检红旗)
  → 制单员并排看"票面原件 vs 字段"逐条核对
  → 提交门：主单号/分单号必须齐全、红旗必须清零，否则不给提交
  → 点提交 = POST /submit
       → 服务端二次校验号非空(不信前端)
       → 回传公司系统【当前=mock，等 IT】
       → 写提交台账 output/submitted.json（谁/何时/号/回执）
       → 派生 (主单号|分单号)→本机原件stem 索引
```

**关键点：只有制单员人工点"提交"才回传公司。** 批处理 / 监控文件夹 / 站点取单这些自动通道**只落盘、绝不自动回传**。
所以"进了台账/索引"= 号齐全、过了门、人工确认过的干净数据。

### 阶段 2：录入员按主单号核对（本期已落骨架）

```
录入员登录(/inputter) → 输入主单号
  → GET /company/mawb
       → 向公司系统取回"主单JSON + 该主单下全部分单JSON"【当前=mock，等 IT】
  → 对每张分单：用 (主单号|分单号) 索引查到本机归档的原件 → 打开票面
  → 对票面核对（主单、分单都核），有不一致处录入员可修改
  → 修改后的 JSON 回传公司系统 + 传给航司接口【触发/失败重试规则待定，未落码】
```

> 说明：录入员"打开分单原件"这一步是**在本机**（制单员阶段 1 已把原件归档在 `output/archive/`），
> 不需要公司再给原件；公司给的是**业务数据 JSON**（主单和分单的字段值）。
> **主单原件**：口子已开（`GET /mawb/source/{主单号}` + 本机 `output/mawb_source/<归一化主单号>/`），
> 现在缺的只是"原件怎么到这台机器上"——见第三节接口 D。

## 三、需要 IT 提供 / 对齐的接口清单

| 接口 | 方向 | 状态 |
|---|---|---|
| **A** 分单数据回传 | 我们 → 公司 | mock 已通，等契约（端点/鉴权/字段字典/回执/幂等） |
| **B** 按主单号取主单+分单 | 我们 → 公司查询 | mock 已通（分单来自本机提交台账），主单字段等 IT |
| **C** 改后回传公司 + 航司 | 我们 → 公司 / 航司 | **规则未定案**，未写码 |
| **D** 主单原件 | 公司 → 我们 | 我方口子已开（`/mawb/source/{mawb}`），只等原件怎么到本机 |


系统已把这层做成**可替换的适配层 `company_api.py`**：现在只实现 mock，
IT 契约到位后填配置 + 补真实现即可，上层流程与权限不动。配置见 `config.py`：

```
COMPANY_API_MODE = mock | live      # 默认 mock；=live 但没接线时系统直接报错，绝不静默返回假数据
COMPANY_API_URL  = <公司网关地址>
COMPANY_API_KEY_ENV = <放密钥的环境变量名>   # 密钥只走环境变量，绝不写进代码/仓库
```

下面 4 个接口是完整闭环所必需的。**报文结构是我们这边的建议初稿，最终以 IT 口径为准**，字段名/大小写/必填性都可以谈。

### 接口 A：分单数据回传（制单员提交时调用）

- 方向：**我们 → 公司**
- 时机：制单员在审核台点"提交"，且该票已过门禁（主/分单号齐全、红旗清零）
- 我们发的内容（单张，JSON）——就是提取+人工核对后的航空口径 40 字段，重点字段：

```json
{
  "mawb": "235-96146363",         // 主单号 MAWB_NO
  "hawb": "CLA26090022",          // 分单号 HAWB_NO
  "shipment": { /* 其余 37 个字段：件数/重量/收发货人/航路/品名/税号… */ },
  "reviewer": "马殿齐",            // 复核人（制单员姓名）
  "reviewed_at": "2026-09-23T10:12:00"
}
```

> 我们**实际**POST 的是整张票据（`/submit`，body 为 `{"tickets":[…]}`）。每张票据带：
> `stem`（本机原件定位键）、`air_reviewed`（人工核对后的航空口径 40 字段，**以此为准**，主/分单号
> 就是其中的 `MAWB_NO`/`HAWB_NO`）、`raw_original`/`air_original`（解析原值，供双方对差异）、
> `needs_review`/`flags`/`acked_flags`（质检状态：还剩哪些红旗、哪些已由人工"确认无误"并留痕）、
> `edited_fields`（人工改过哪些字段）、`reviewer`/`reviewed_at`。
> 上面 `{mawb,hawb,shipment}` 那种紧凑结构是我们**建议公司侧接收的形态**——我方愿意在适配层
> （`company_api.submit_order`）里按你们的字段字典做映射，你们只要给字段字典和回执格式。

- **需要 IT 明确**：
  1. 接收端点 URL、HTTP 方法（POST？）、是否批量（一次多张）还是单张。
  2. 鉴权方式（Token / 签名 / IP 白名单？密钥怎么给我们）。
  3. 字段字典：公司侧对 40 字段的**确切字段名、类型、必填、枚举取值**（尤其主单号前三位、校验位、连字符写法）。
  4. **回执格式**：受理成功/失败怎么返回，失败原因码，我们要写进提交台账。
  5. 幂等：同一张票重复提交如何处理。

### 接口 B：按主单号取主单+分单数据（录入员检索时调用）

- 方向：**我们 → 公司发查询 → 公司返回**
- 时机：录入员在检索台输入主单号点检索
- 我们发的查询：`{ "mawb": "235-96146363" }`
- 我们需要拿回（建议结构）：

```json
{
  "mawb": "235-96146363",
  "mawb_order": { /* 主单业务字段 JSON */ },
  "hawb_orders": [
    { "hawb": "CLA26090022", "shipment": { /* 该分单字段 */ } },
    { "hawb": "CLA26090023", "shipment": { /* … */ } }
  ]
}
```

> 我们的处理：拿到返回列表后，每张分单再用 `(主单号|分单号)` 去本机索引查它归档的原件 stem，
> 让录入员能把"公司给的 JSON"和"本机票面原件"摆一起对。所以**返回里必须带上能和票面原件对上的分单号**。
- **需要 IT 明确**：
  1. 查询端点、方法、参数名。
  2. 主单业务字段清单（接口 A 的 40 字段是否同源？主单独有字段有哪些？）。
  3. 一个主单号下若有多张分单，是否全量返回、有无分页。
  4. 查不到该主单号时的返回（空？错误码？）。

### 接口 C：核对修改后的回传（公司 + 航司，两路）

- 方向：**我们 → 公司**、**我们 → 航司接口（第三方提供）**
- 时机：录入员核对/修改后，把改动同时回传公司系统并送航司
- **这块规则目前未定案**，需要 IT / 业务共同确认后才落码：
  1. 触发时机：录改一次就回传？还是录入员点一个"确认"才回传？
  2. 修改范围：主单、分单两边都能改，改后两路是否都要发？
  3. **航司接口是谁提供、报文口径**（航司那边有独立的对接方/文档，需要一并拿到）。
  4. **部分失败**：回公司成功、发航司失败时怎么办（倾向"标记失败 + 可重试"，待确认）。

### 接口 D（可选）：主单原件预览 —— 我方口子已开好

- 若主单也有票面原件、录入员需要"对票面"核对主单，则需公司给主单原件的**下载或预览地址**。
- **我方已实现（不需要再等前端）**：`GET /mawb/source/{mawb}`（录入员或管理员会话），按归一化主单号到
  `output/mawb_source/<主单号>/` 取原件，格式处理与分单侧同一套：PDF/图片直接在线预览，Excel 电子单
  现转 PDF 缓存；`?raw=true` 发原件本身供下载。检索结果里的 `source_available` 就是"这台机器上有没有这张主单的原件"。
- **所以 IT 只要给以下任一种**，我们这边就在适配层把原件落到那个目录，路由与页面一行都不用改：
  1. 主单原件的下载 URL（我们拉一次缓存进目录）；
  2. 查询接口（接口 B）里直接带回原件（base64 或文件流）；
  3. 公司/运维人工把 PDF 放进 `output/mawb_source/23596146363/` 这样按主单号建的目录（今天就能用）。
- **需要 IT 明确**：主单原件是否存在、格式（大概率 PDF？）、怎么取（URL / 下载接口 / 报文内嵌）。

## 四、主/分单号"对齐口径"——这是最容易埋雷的地方，请重点确认

录入员能否按主单号把"公司数据"和"本机原件"对上，**完全取决于两边单号写法是否一致**。

- 我们已做归一化：**大写 + 去掉空格/连字符等非字母数字字符**。
  - `235-96146363` 与 `23596146363` 与 `235 96146363` → 归一后同键 ✅（格式差异挡得住）
- 归一化**挡不住语义差异**，需要 IT 确认：
  1. 公司的主单号/分单号字段，是否包含**前三位（承运人航司码）**？校验位算不算在内？
  2. 主单号在公司系统里会不会重复？（我们按"主单号不重复"设计复合键唯一性）
  3. 分单号大小写、前缀（如 `CLA` 字母段）两边写法是否一致？
  4. 公司返回的号和我们票面提取的号，若偶发不一致，以哪边为准？

## 五、当前实现状态一览

**已落码并跑通（本地，无真实外部调用；回归 143 项全绿）**

- 提交门禁：制单员缺主/分单号或未清红旗 → 前端拦 + 后端 `POST /submit` 二次拒绝。
- 提交台账 `output/submitted.json` + `(主单号|分单号)→stem` 复合键索引（原子写、600 权限、线程安全）。
- 录入员角色 `inputter`：种子账号刘明/郭健康/郭旭（口令空，待管理员下发）；权限守卫 `require_inputter`（录入员或管理员可用检索，制单员 403）。
- 公司适配层 `company_api.py`：`search_mawb` / `submit_order` 的 mock 实现，live 未接线时抛错，绝不伪造数据、绝不外发。
- `GET /company/mawb` 检索端点 + 录入员检索台页面 `/inputter`（检索 → 列分单 → 打开本机原件）。
- 主单侧两个"接口一到即可用"的口子：`GET /mawb/source/{mawb}` 主单原件预览（原件目录按归一化主单号建）；
  检索页对 `mawb_order` **按返回的 key 通用渲染**成字段表——IT 给什么字段就显示什么，前端不需要再改一轮。

**待 IT / 待业务定案（所以现在没写码）**

- 接口 A/B/C/D 的真实调用（等契约）。
- 主单业务字段解析成结构化字段那条线。
- 主↔分单**一致性对比的具体字段与规则**。
- 修改后"回公司 + 传航司"两路的触发时机与部分失败重试。

## 六、给 IT 的一句话总结

> 我们这套已经把"提取 → 制单员核对提交 → 按主单号检索本机原件"的**内部闭环跑通**，只差和公司系统对接的**四张接口
> （A 分单回传、B 主单+分单查询、C 改后回传公司/航司、D 主单原件预览）**。请你们给出这 4 个接口的
> **端点、鉴权、字段字典、回执格式**，特别是**主/分单号写法能否和我们票面提取的对齐**（第四节）。
> 接口一到，我们在 `company_api.py` 填实现 + 配 `COMPANY_API_MODE=live` 即可上线，内部流程无需改动。
